# 프로젝트 구조 및 버그 재점검

점검일: **2026-10-19**. 현재 작업 트리의 코드·리소스·문서를 기준으로 검토했다. 아래의 재현 결과와 정적 검토상 우려를 구분한다. 게임 코드·콘텐츠·밸런스는 변경하지 않았고, 테스트는 `.godot` 아래 별도 저장소를 사용했다.

## 전체 판단

수입·구매·이벤트·화면을 나눈 현재 디렉터리 구조는 유지할 만하다. 당장 폴더를 다시 나누기보다는 **큰 수 타입의 UI 경계, 신호를 내보내는 시점, 저장 복원의 일관성, 테스트·문서의 동기화**를 먼저 다루는 편이 효과적이다.

현재 구성은 **수입원 4개, 구매 버튼 28개, Autoload 10개**다. `RightPanelManager`, 짬 환생 연출, 수익 누계가 추가되어 이전 점검의 전제와 달라졌다. 메인 장면의 기본 구성과 새 환생 데이터의 저장·복원은 별도 검사에서 정상 동작했다.

## 확인된 문제

### 1. 큰 수 업그레이드 가격에서 UI 스크립트 오류 — 수정 완료

- 위치: [IncomeUpgradePanel.gd](../ui/IncomeUpgradePanel.gd), `_refresh_row()`.
- `cost`는 `float` 또는 `BigNumber`인 `Variant`인데, 버튼 비활성화 조건에서 `cost <= 0.0`으로 직접 비교한다.
- 자판기 레벨을 5,000으로 설정한 뒤 실제 업그레이드 패널을 생성하면 `Invalid operands 'Object' and 'float' in operator '<='`를 재현한다. 이때 가격은 약 `2.2008e381`이다.
- 계산과 가격 표시는 큰 수를 지원하지만 해당 행의 갱신은 중단된다. `ErrorManager` 이력도 0개라 사용자 오류 창으로 안내되지 않는다. 엔진 스크립트 오류가 자동으로 공통 오류 창에 전달되는 구조는 아니다.
- 권장: 이 비교를 `BigNumber.compare`로 통일하고, 실제 업그레이드 패널에 큰 수 가격을 넣는 검증을 추가한다.

후속 수정: 비교를 `BIG.compare(cost, 0.0) <= 0`으로 변경했다. `tests/income_upgrade_panel.tscn`에서 일반 가격과 레벨 5,000의 큰 수 가격에 대해 표기, 자금 부족/충족에 따른 활성 상태·음영, 구매 후 레벨·잔액·UI 갱신을 검증했다. headless 실행에서 PASS를 확인했고 엔진 오류·경고는 없었다. 아래 재현 설명은 수정 전 기록이다.

### 2. 업그레이드 결제 중 재진입하면 같은 가격으로 두 레벨 구매 — 해결

2026-10-19 후속 수정: 수입원별 잠금을 결제·레벨·수입 신호 처리 완료까지 유지한다. 결제가 성공하면 잔액과 레벨을 함께 반영한 뒤 `money_changed`를 발행하므로, 신호 안에서 저장해도 차감 금액과 레벨이 일치한다. 결제·알림 콜백에서 초기화·환생·불러오기가 발생하면 `_runtime_generation`을 확인해 이전 업그레이드의 후속 알림을 중단한다. 잠금은 호출이 끝날 때 해제하며 다른 수입원의 구매는 허용한다.

`tests/income_upgrade_reentrancy.tscn`에서 결제·레벨·수입 알림의 재호출, 순차 구매의 30원 + 68원 차감, 신호 중 저장·불러오기·초기화·환생, 결제 실패 후 재시도, 다른 수입원과 큰 수 가격을 검증했다. 해당 테스트와 `income_upgrade_panel`, `big_number_payments`가 모두 PASS했다. 아래는 수정 전 재현 기록이다.

- 위치: [IncomeManager.gd](../autoload/IncomeManager.gd), `upgrade_source()` 253~272행. [EconomyManager.gd](../autoload/EconomyManager.gd), `_apply_money_delta()` 67행 이후.
- 업그레이드가 결제 신호를 내보낸 뒤 레벨을 올린다. `money_changed` 구독자가 같은 수입원의 업그레이드를 한 번 더 요청하면 두 요청 모두 이전 레벨의 가격을 사용한다.
- 재현: 자판기 레벨 1, 자금 100,000원에서 일회성 `money_changed` 콜백으로 업그레이드를 재호출했다. **레벨 3까지 총 60원 차감**됐다. 정상 순차 구매는 30원 + 68원 = 98원이다.
- 현재 기본 UI의 연속 클릭만으로 발생한다고 확인한 문제는 아니다. 동기 신호 구독자의 재호출이 조건이며, 자동 구매 등의 확장 시 드러날 수 있다. 버튼 구매에는 재진입 방지가 있지만 수입원 업그레이드에는 없다.
- 권장: 수입원별 구매 진행 잠금과 상태 세대 검사, 결제·레벨 변경 완료 후 신호 발행을 일관되게 적용한다. 로드·환생이 결제 콜백에서 발생하는 경우도 같은 경계에서 다룬다.

### 4. 구조 안내 문서가 현재 환생 시스템과 충돌 — P2

- 위치: [GameOverview.md](../GameOverview.md), 27~43행·해금 조건·Autoload 표. 비교 문서: [JJAM_PRESTIGE.md](JJAM_PRESTIGE.md).
- 개요는 수입원 3개·버튼 27개, `floor(sqrt(현재 자금 / 1,000,000))` 환생 보상, 확정 짬만을 `total_jjam`으로 설명한다.
- 코드는 수입원 4개·버튼 28개이며, `floor(짬 해금 이후 이번 환생의 누적 수익 / 50억)`에 첫 환생 전 400짬을 더한다. `total_jjam`은 **확정 짬 + 미확정 짬**, 수입 보너스는 **확정 짬**을 사용한다. `RightPanelManager`도 Autoload 표에서 빠져 있다.
- `docs/JJAM_PRESTIGE.md`가 새로 생겨 통합 개요와 설명의 기준이 다시 나뉘었다. 옛 점검의 큰 수 미지원 설명도 아래 과거 기록으로만 읽어야 한다.
- 권장: 현행 기획·코드 안내의 기준을 `GameOverview.md` 하나로 맞추고, 규칙 변경 시 관련 테스트와 같은 변경 단위로 갱신한다. 미확정 짬이 해금에 포함되는 현재 동작이 의도인지도 기준 문서에 명시한다.

## 정적 검토상 우려

아래는 현재 코드 경로에서 확인한 위험이다. 해당 환경·손상 상황을 실제 배포물에서 재현한 결과와는 구분한다.

### 5. 저장 초기화 실패 후에도 게임이 진행됨 — P2

- 위치: [main.gd](../scenes/main.gd), 51행. [SaveManager.gd](../autoload/SaveManager.gd), 23~52행.
- 메인 장면은 `SaveManager.initialize()`의 실패 반환값을 확인하지 않는다. 저장 폴더 생성·이전 실패 시 `initialized`는 false지만 구매·생산 화면 구성은 계속 진행한다.
- 반면 이벤트는 `SaveManager.initialized`를 검사하므로 시작되지 않으며 자동 저장도 수행되지 않는다. 오류 창을 닫은 뒤 플레이는 되는 것처럼 보이지만 저장과 이벤트가 빠진 상태가 될 수 있다.
- 릴리스 저장 위치가 실행 파일 옆 `saves`이므로, 해당 위치에 쓰기 권한이 없는 설치·실행 환경에서는 이 경로가 중요하다. 실제 모바일·설치형 배포 검증은 이번에 하지 않았다.
- 권장: 초기화 성공을 게임 시작의 명시적 조건으로 삼거나, 사용자 데이터 위치로 대체하고 실제 저장 가능 상태를 UI에 반영한다.

### 6. 새 연출·UI 경로에는 공통 검증과 잠금 복구가 충분히 연결되지 않음 — P2

- 위치: [JjamPrestigePresentation.gd](../scripts/JjamPrestigePresentation.gd), 63~89·187~240행. [JjamPrestigePanel.gd](../ui/JjamPrestigePanel.gd), [EventRewardDeposit.gd](../ui/EventRewardDeposit.gd)의 필수 노드 접근.
- 짬통 소개는 입력을 잠근 뒤 텍스처·`peek_frames`·`open` 애니메이션의 마지막 프레임을 직접 읽고, 정상 완료 신호가 와야 잠금을 해제한다. 타입·프레임 누락으로 중간에 스크립트 오류가 나면 `_end_intro()`까지 가지 못할 수 있다.
- 새 UI 상당수는 `$노드경로`나 `get_node()`를 직접 사용한다. 해당 노드가 이동·삭제되면 `ErrorManager.require_node()`·`initialize_component()`로 안전하게 비활성화하는 경로를 거치지 않는다.
- 권장: 잠금 전에 연출에 필요한 데이터를 검증하고, 실패·취소·시간 초과가 모두 공통 종료 함수에서 UI와 입력을 복구하도록 한다. 현행 자산의 정상 소개 연출에서 멈춤을 확인했다는 뜻은 아니다.

## 권장 순서와 검증 범위

1. 큰 수 UI 비교를 바로잡고 재현 사례를 회귀 검사로 남긴다.
2. 업그레이드의 결제·상태 변경·신호 순서와 재진입 방지를 정리한다.
3. 옛 테스트를 현 규칙·UI에 맞추고, 새 짬·저장 이전·연출 중 슬롯 전환을 검증한다.
4. 저장 초기화 실패와 연출 실패의 복구 경로를 정리한다.
5. 개요 문서를 현행화한 뒤 상태 복원·ID 조회·화면 갱신의 결합을 줄인다.

이번에는 Godot 4.7.2의 headless 실행과 코드·데이터 검토를 사용했다. 실제 렌더러의 시각적 배치, 모바일 입력, 릴리스 내보내기, 장시간 플레이의 성능은 검증 범위에 포함하지 않았다.

실행 로그: `.godot/review_20261019_{big_numbers,big_number_payments,save_system,events,jjamtong_hover,probe,main}.log`. `probe`는 큰 수 UI·재진입·이벤트 중복 검사, `main`은 별도 저장소에서 메인 구성과 새 환생 저장 복원 검사다. 정상 종료 코드만으로 스크립트 오류가 없다고 판단하지 않았으며 로그 내용을 함께 확인했다.

# 프로젝트 구조 및 버그 점검

점검일: 2026-10-08. 후속 수정: 2026-10-09. 기존 작업 중인 변경을 유지하면서 실행 로직과 상태 갱신을 정리했다. 게임 콘텐츠, 구매 가격, 생산량, 기존 콘텐츠의 해금 순서는 변경하지 않았다.

2026-10-14 후속: 아래 1·2번에서 지적한 자금·수입·가격의 표현 범위와 환생 보상 한계는 가수·지수 자료형으로 확장했다. 큰 값은 유효숫자를 제한해 근사하며, 기존 저장의 정수는 그대로 읽는다. 현재 표시 규칙·정밀도·지원 범위는 [큰 수 문서](../GameOverview.md#큰-수-표시와-계산)를 참고한다.

## 구조

현재 규모에는 아래 역할 분리가 적절하다. 디렉터리를 재배치하기보다 각 계층 사이의 상태 변경 알림을 보완했다.

| 위치 | 책임 |
| --- | --- |
| `autoload/EconomyManager.gd` | 자금과 전체 수입·시간 배율 |
| `autoload/IncomeManager.gd` | 수입원 활성 상태, 레벨, 생산 진행 및 지급 |
| `autoload/ButtonManager.gd` | 구매 가능 여부, 결제, 효과 적용, 해금 상태 |
| `autoload/PrestigeManager.gd` | 환생 보상과 초기화 순서 |
| `autoload/ErrorManager.gd` | 공통 검증, 오류 메시지 표시, 중복 알림 방지 및 오류 이력 |
| `data/`, `scripts/ResourceInit/` | 콘텐츠 정의와 리소스 형식 |
| `scenes/world_layout.tscn` | 월드 배치와 렌더링 깊이 |
| `scenes/main.gd`, `ui/` | 장면 조립, 입력, 화면 표시 |

## 수정한 문제

- **환생 후 화면 잔류:** 구매 상태는 초기화돼도 해금 여부가 계속 `false`인 버튼은 갱신 신호가 없었다. 모든 버튼에 초기화 알림을 보내 구매 그림과 클릭 영역을 갱신하도록 수정했다. 수입원 초기화도 활성 상태·타이머·레벨 변경을 알린다.
- **업그레이드 목록 중복:** `queue_free()`만 호출하면 같은 프레임의 재구성에서 이전 행이 남았다. 부모에서 즉시 분리하고 삭제를 예약하며, 재구성 때 누르고 있던 업그레이드도 중지한다. 수입 변화에 대한 구독을 통합했다.
- **환생 중 말풍선 잔류:** 프레임 대기 중이던 말풍선이 초기화 뒤에도 꼬리와 타이머를 다시 켰다. 초기화 때 말풍선을 숨기고, 대기 이후 구매 상태를 재확인한다.
- **결제 신호에 의한 중복 구매:** 결제 도중 `money_changed`의 구독자가 같은 구매를 요청하면 두 번 차감하고 효과도 두 번 적용할 수 있었다. 진행 중인 구매에 대한 재진입을 차단했다.
- **효과 없는 결제:** 존재하지 않는 수입원이나 적용 불가능한 배율 효과를 구매할 수 있었다. 효과 대상과 배율 곱의 유효성을 결제 전에 확인한다.
- **초고속 생산의 정수 범위 초과:** 완료 회차를 `floori()`로 변환하던 부분을 부동소수점 회차 계산으로 바꾸고, 남은 시간은 나머지 연산으로 보존한다. 일반적인 생산, 긴 프레임, 속도 변경 시 진행률 유지도 검증했다.
- **자금·배율의 무한대 오염:** 입력 각각이 유한해도 덧셈·곱셈 결과가 무한대일 수 있었다. 유효하지 않은 결과가 기존 상태를 덮어쓰지 않게 했다. 이는 큰 수 지원의 대체 수단은 아니다.
- **숫자 표시 오류:** `999.999`가 `999.00`으로 표시되는 자리올림 오류를 수정했다. 0.01 미만의 양수는 과학적 표기로 표시하여 빠른 생산 시간이 0초로 보이지 않게 했다.
- **화면 갱신 및 위치:** 전체 수입 배율 변경이 수입 화면에도 전달되게 했다. 월드 배치 부모의 위치·크기가 변경되면 생산 타이머와 카메라 가로 범위가 어긋나는 문제를 수정했다. 구매 UI와 말풍선도 부모 좌표계를 고려한다.
- **구매 애니메이션 중첩:** 애니메이션이 끝나기 전에 다시 재생하면 중간 크기나 0을 원래 크기로 저장할 수 있었다. 이전 애니메이션을 중지하고 최초 크기로 복원한다.

## 남아 있는 위험

### 1. 큰 수의 정확도와 표현 범위 — 높음

`EconomyManager.money`, 배율, 가격, 생산량은 [정밀도에 한계가 있는 Godot의 `float`](https://docs.godotengine.org/en/stable/classes/class_float.html)이다. 최초 점검에서는 자금 `1e20`원일 때 `spend_money(1.0)`이 성공해도 잔액은 바뀌지 않았다. 후속 수정에서는 증감이 완전히 사라지는 경우 `PRECISION_LOSS`를 표시하고 실패를 반환한다. 유효하지 않은 수치 결과도 표시하고 거절한다. 한도를 넘는 수입을 저장하는 문제, 부분적으로 반올림되는 정밀도 손실, 지수형 업그레이드 가격과 여러 배율을 곱한 최종 생산량의 표현 범위는 남아 있다.

큰 수를 계속 키우는 게임 설계를 유지하려면 자금·가격·생산량·배율을 함께 다루는 가수/지수 또는 임의 정밀도 수치 형식이 필요하다. 표시만 과학적 표기로 바꾸면 계산 정확도는 해결되지 않는다.

### 2. 환생 보상의 정수 범위 초과 — 높음

`PrestigeManager.get_current_jjam()`의 `floori()`와 `total_jjam: int`에는 별도의 정수 한계가 있다. 최초 점검에서는 자금 `1e45`원의 환생 보상이 조용히 0으로 계산되었다. 후속 수정에서는 변환 전 보상 범위와 누적 덧셈 범위를 검사하며, `JJAM_OVERFLOW`를 표시하고 자금·구매 상태를 유지한 채 환생을 중단한다. 표현 범위를 넘는 보상을 실제로 저장하려면 여전히 큰 수 형식이 필요하다.

### 3. 문자열 ID와 수동 등록의 결합 — 중간

버튼 ID, 효과 대상, 해금 조건의 `value`, 월드 노드 이름이 문자열로 연결된다. `ButtonManager.buttons`와 `IncomeManager.sources`에도 각각 등록해야 한다. 중복 ID는 검색 결과와 런타임 딕셔너리 상태를 다르게 만들 수 있고, 월드 노드 이름이 틀리면 구매 로직이 존재해도 화면 구성에서 빠질 수 있다. 순환 해금 조건은 진행을 막는다.

후속 수정으로 `ErrorManager`가 시작 시 등록 목록·참조·해금 순환을 검사한다. 실행 중 조회에서도 누락·중복 ID를 알리고 임의의 항목을 반환하지 않는다. 월드 노드 이름의 중복·누락과 이미지·클릭 영역 문제도 감지하며 해당 버튼의 구매를 차단한다. 잘못된 필수 UI 노드는 해당 화면의 동작을 중단한다. 현재 콘텐츠의 전체 구매 경로와 의도적으로 잘못된 구성을 넣은 검증이 통과했다.

### 4. 미처리 해금 조건 — 해결

`UPGRADE`를 `TOTAL_JJAM`으로 교체했다. `amount`에 필요한 누적 짬을 지정하며, `PrestigeManager.total_jjam`을 기준으로 판단한다. 예상 환생 보상은 포함하지 않는다. 환생 완료 때 해금 상태를 다시 계산하며, 잘못된 조건 종류나 소수 짬 기준은 오류를 표시하고 거절한다.

### 5. 개발자 도구의 배포 노출 — 수정 완료

`main.gd`의 O 키 처리에 `OS.is_debug_build()` 검사를 추가했다. 개발자 도구는 디버그 빌드에서만 O 키로 열 수 있으며, 출시 빌드에서는 해당 키 입력을 처리하지 않는다.

### 6. 배치 정보 중복 — 낮음

`IncomeSourceData.display_position`과 `display_scale`은 리소스에 남아 있지만 실제 생성 위치는 `world_layout.tscn`에서 읽는다. 리소스의 이 값을 수정해도 월드 배치는 바뀌지 않는다. 현재는 월드 장면을 배치의 기준으로 사용해야 한다. 기존 리소스의 호환성을 유지하기 위해 필드를 삭제하지 않았다.

## 검증

이 점검 당시에는 Godot 4.7.2에서 계산·구매·환생 UI, 렌더링 깊이, 잘못된 데이터와 오류 표시를 세 회귀 테스트로 검증했다. 이후 기존 테스트는 모두 삭제하고 최저가 구매 밸런스 테스트로 교체했다. 현재 실행 명령은 다음과 같다.

```text
godot --headless --path . --fixed-fps 60 res://tests/balance_playthrough.tscn
```

현재 테스트는 해금된 버튼과 활성 수입원의 레벨업 중 가장 싼 항목을 선택해 실제 게임의 생산과 구매를 진행한다. 버튼별 가격과 구매 시간, 전체 구매 경로는 `res://logs/balance_playthrough.txt`에 저장한다. 기존 회귀 테스트의 모든 검증 범위를 포함하지는 않는다. 실제 모바일 터치 입력과 출시용 내보내기는 이 점검에 포함하지 않았다.

오류 객체의 책임과 사용법은 GameOverview.md의 [오류 처리 항목](../GameOverview.md#오류-처리)을 참고한다. 게임 시작 전의 문법 오류·필수 `preload` 실패 등 엔진 오류 전체를 가로채는 객체는 아니다.
