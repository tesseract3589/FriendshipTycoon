## 게임플레이
1. 기본 자금으로 income source를 구매하여 일정 시간당 일정량의 돈을 번다.
2. income source를 업그레이드하고, income을 multiply하는 여러 버튼들을 구매해 자금을 점점 불려 나간다.
3. 새로운 income source를 구매하고 과정을 반복한다. (경우에 따라서는 먼저 structure를 구매해야 다음 income source가 해금될 수 있다)
4. 기하급수적으로 자금을 불리다 보면 '짬'이 모인다. (또 다른 재화)
5. 환생하면 모든 버튼이 초기화되는 대신 그동안 모인 '짬'의 수만큼 multiplier가 적용된다. (1짬 = +1% multiplier)
6. 짬을 사용하여 편의성 업그레이드를 구매할 수 있다. (버튼 원격 구매 등)
7. 짬 또한 기하급수적으로 오르게 된다. 어느 정도 짬이 모이면 2번째 prestige layer인 '재입대'를 할 수 있게 된다.
8. 재입대를 할 시 무공훈장 레벨이 한 단계씩 오르며, 모든 income source의 생산 시간이 50배 줄어든다.
9. (추가 예정 컨텐츠) 명예의 전당. 명예의 전당에 있는 모든 버튼 구매는 짬 환생이나 재입대로 초기화되지 않는다. 이곳에서는 global multiplier를 주로 업그레이드할 수 있다.
10. 명예의 전당 꼭대기까지 구매하면 마지막 prestige layer이자 엔딩인 '초월' 환생이 해금된다.
11. 초월을 하면 카르마가 한 단계 오르게 되는데, 이 카르마를 사용하여 버튼을 초월해도 사라지지 않는 영구 구매 상태로 만들 수 있다. (명예의 전당은 영구 구매 불가능)

## 특징
- multiplier가 항상 파격적으로 적용되기 때문에 자금이 기하급수적으로 불어난다.
- integer 범위에서 벗어나는 연산을 해야 할 수 있어서 특수 formula가 필요하다.
- 자금·가격·수입은 `만 → 억 → … → 무량대수`의 이만체진 단위와 최대 소수점 네 자리로 반올림하고 끝의 0을 생략한다. 예: `1.234만원`, `22억원`. 10,000 무량대수부터 `1.XXXX만 x 10^X`로 표시하며, 기존 수치 범위를 넘는 값은 가수·지수로 계산한다. [큰 수의 표시·계산·저장과 입력 방법](docs/BIG_NUMBERS.md).
- 빠른 생산 주기와 툴팁의 시간은 소수 둘째 자리까지 표시한다. 현재 단위에서 `0.01` 미만이면 `s → ms → μs → ns → ps → fs → as → zs → ys → rs → qs` 순서로 1,000배씩 변환한다. 예: `0.0099s`는 `매 9.90ms`. `0.01qs` 미만에서는 `qs`를 유지하고 과학적 표기법을 사용한다. 단위 기준: [Less than one second](https://en.wikipedia.org/wiki/Orders_of_magnitude_(time)#Less_than_one_second).

## 해금 조건

`ButtonData.unlock_condition`에 `UnlockCondition` 리소스를 연결한다.

| Type | 기준 | 설정 |
| --- | --- | --- |
| `MONEY` (0) | 현재 자금 | `amount` 이상이면 해금 |
| `TOTAL_JJAM` (1) | 환생으로 확정된 누적 짬 | `amount`에 0 이상 정수를 지정 |
| `BUTTON` (2) | 선행 버튼 구매 | `value`에 선행 버튼 ID 지정 |

- 기존 `UPGRADE` 자리를 `TOTAL_JJAM`으로 교체했다. 직렬화된 enum 번호는 유지하며, 기존 `MONEY`와 `BUTTON` 조건은 그대로 동작한다.
- 누적 짬은 `PrestigeManager.get_total_jjam()`으로 읽는다. 현재 자금으로 계산한 예상 환생 보상은 해금 기준에 포함하지 않는다.
- 환생 완료 신호(`prestige_changed`)를 받으면 `ButtonManager`가 해금 상태를 다시 계산한다.
- 기존 콘텐츠에 누적 짬 조건을 임의로 지정하지 않았다. 필요한 버튼의 리소스에서 `TOTAL_JJAM`과 `amount`를 설정하면 된다.

## 수입원 업그레이드 밸런스

- 가격은 레퍼런스의 선형 × 지수 곡선을 사용한다. 현재 레벨을 L, 구매한 업그레이드 횟수를 `k = L - 1`로 놓으면 `C(L) = C₀ × (1 + 0.8k) × 2^(k/4)`다. 수입원별 `upgrade_base_cost`, `upgrade_cost_linear_growth`(기본 0.8), `upgrade_cost_doubling_levels`(기본 4)로 조정한다. 첫 업그레이드 가격은 자판기 **30원**, 간부식당 **10,000원**, 간부목욕탕 **5,000,000원**이다.
- 수입 증가 곡선은 각 `data/IncomeSources/*.tres`의 **Upgrade Income**에서 조정한다. `upgrade_first_income_ratio`가 첫 증가율이며 **0.3은 +30%, 1.2는 +120%**다. `upgrade_income_decay`는 이후 증가율이 낮아지는 강도이며 **클수록 더 빠르게 낮아진다**. 0이면 매번 같은 증가율을 적용한다. 새 수입원의 기본값은 0.3과 4.0이다.
- 수식은 `다음 증가율 = first_income_ratio / (1 + income_decay × (현재 레벨 - 1))`, `다음 회당 수입 = 현재 회당 수입 × (1 + 다음 증가율)`이다. 배율과 반올림을 적용하기 전 수입을 기준으로 누적 계산한다. 예를 들어 식당의 증가율은 **30% → 6% → 3.33% → 2.31%**로 낮아진다. 가격과 수입 곡선은 각각 조정할 수 있다.
- 현재 자판기는 `upgrade_first_income_ratio = 1.2`, `upgrade_income_decay = 0.67`이며 첫 회당 수입이 **10원→22원**이다. 식당과 목욕탕은 각각 `0.3`, `4.0`을 사용해 **30,000원→39,000원**, **12,000,000원→15,600,000원**이 된다. 모든 수입원이 첫 업그레이드에서 최소 30% 증가하도록 맞췄다. 이후에는 현재 수입에 대한 증가율이 계속 낮아진다.
- 수입원·전체 수입 배율을 적용한 최종 회당 금액을 원 단위로 반올림한다. 양수가 0으로 반올림되는 경우에는 원래 소액을 보관해 누적한다. 완료 회차는 프레임마다 모아 원 단위 금액을 지급하고 소수 원과 계산 잔여값은 수입원에 남긴다. 툴팁과 업그레이드 패널의 초당 수입은 회당 금액을 생산 주기로 나눈 값을 표시한다. 예를 들어 10원/7초는 `초당 1.43원`, 패널에서는 `10원/회, 초당 1.43원`이다. 10,000 미만은 최대 소수점 두 자리, 그 이상은 최대 네 자리의 한국식 큰 수 단위로 반올림하며 끝의 0을 생략한다. 예: `2원`, `1.5원`, `1.234만원`. HUD 총수입도 수입원별 초당 수입을 반올림하지 않고 합산한 뒤 같은 표시 규칙을 적용한다. 업그레이드 패널은 다음 레벨과 현재 레벨의 회당 금액 차이를 표시한다. 자판기 Lv.1에서는 `다음 레벨 +12원/회`, Lv.2에서는 `다음 레벨 +16원/회`다. 누적 수입은 캐시로 관리하며 기본 수입·첫 증가율·감소 강도를 바꾸면 다시 계산하고 환생하면 초기화한다.
- 현재 목욕탕을 포함한 18개 버튼의 최저가 구매 경로를 기준으로, 수입 곡선 변경 전 완료 시간은 **1779.67초(29분 39.67초)**, 변경 후는 **1787.75초(29분 47.75초)**로 **+0.45%**다. 간부식당 구매는 **168.33초(2분 48.33초)**, 유리문 해금은 **731초(12분 11초)**이며 유리문 구매가 최종 완료 시점이다. 변경 전 결과는 `res://logs/balance_playthrough_before_curve.txt`에 보관했다. 클릭 지연과 구매 선택에 따라 실제 플레이 시간은 달라진다.
- 밸런스 테스트: `godot --headless --path . --fixed-fps 60 res://tests/balance_playthrough.tscn`. 자금 0원·짬 0으로 시작하고, 해금된 미구매 버튼과 활성 수입원의 다음 레벨업 중 항상 가장 싼 항목을 선택한다. 자금이 부족하면 실제 생산 주기를 60FPS 가상 시간으로 진행하며 매 프레임 다시 비교한다. 같은 가격은 버튼 우선, 이후 등록 순서다. 모든 버튼 구매 시 종료하며 환생·외부 자금·클릭 지연은 없다.
- 결과는 `res://logs/balance_playthrough.txt`에 실행할 때마다 덮어쓴다. 버튼별 가격·누적 구매 시간·해금 시점과 레벨업을 포함한 전체 구매 기록을 저장한다. 첫 실제 증가가 최소 30%인지, 레벨이 높아지면 증가율이 낮아지는지, 설정 변경 시 캐시가 갱신되는지, 다음 레벨 미리보기와 실제 금액이 일치하는지도 검사한다. 식당 구매 2~3분·유리문 해금 최소 10분·완료 시간 **변경 전의 ±5%**를 확인한다. 테스트의 `TARGET_COMPLETION_SECONDS`와 `COMPLETION_TIME_TOLERANCE`에서 완료 시간 기준을 조정할 수 있다. 실패해도 그때까지의 기록을 저장한다.

## 로컬 진행 저장

- 게임 실행 파일 옆에 `saves` 폴더를 만든다. 디버그 빌드는 `res://saves`에 저장한다. `autosave.cfg`의 자동 저장 슬롯 1개와 `slot_01.cfg`~`slot_10.cfg`의 수동 슬롯 10개를 생성하며, 아직 진행을 저장하지 않은 슬롯은 비어 있음으로 표시한다.
- **자동 저장 슬롯**은 번호 없이 주황색으로 표시한다. 게임 종료 시 저장하고 다음 실행 때 자동으로 불러온다. 화면 우측 상단 **저장** 버튼을 누르면 슬롯 선택 창이 열리며, 자동 슬롯은 수동 저장을 막는다. 선택된 슬롯은 흰색 테두리로 표시한다. 모바일에서는 백그라운드 전환 시에도 자동 저장한다.
- 슬롯 1~10은 수동 저장용이다. 슬롯을 선택한 뒤 **저장** 또는 **불러오기**를 누른다. 덮어쓰기와 불러오기는 확인 창을 거친다. 저장 시각과 자금이 표시된다.
- 빈 슬롯도 **불러오기**로 선택할 수 있다. 새 게임 시작 안내를 확인하면 자금·구매·업그레이드·환생 진행을 모두 초기화하여 자판기도 구매하지 않은 상태로 시작한다. 빈 슬롯은 저장하기 전까지 비어 있으며, 다른 슬롯의 저장 데이터는 유지된다. 자동 저장 슬롯이 비어 있는 경우에도 다음 실행은 초기 상태로 시작한다.
- 선택한 슬롯의 **초기화** 버튼을 누르면 되돌릴 수 없다는 경고 창이 뜬다. **초기화**를 확인해야 해당 슬롯의 저장 데이터를 비우며, **취소**하면 유지한다. 현재 플레이 진행은 유지하며, 비어 있는 슬롯은 초기화 버튼을 비활성화한다. 자동 저장 슬롯도 초기화할 수 있고, 게임 종료 시 현재 진행으로 다시 자동 저장됨을 경고 창에 안내한다.
- 이전 구성의 자동 슬롯 1은 `autosave.cfg`로, 수동 슬롯 2~10은 새 슬롯 1~9로 옮긴다. 새 수동 슬롯 10은 비어 있는 상태로 추가한다. 원본 파일 내용은 `legacy_slots_v1.cfg`에 백업하고, 중간에 이동이 실패하면 다음 초기화에서 백업을 기준으로 재시도한다.
- 자금과 입출금 잔여값, 전체·수입원·개발자 배율, 수입원 활성화·레벨·남은 생산 시간·미지급 수입과 잔여값, 버튼 구매·영구 구매 상태, 환생 재화를 저장한다. 불러올 때 구매 효과를 다시 적용하지 않는다. 게임을 끈 동안의 수입은 계산하지 않는다.
- 파일 전체를 검증한 뒤 진행을 복원한다. 저장은 임시 파일을 완성한 뒤 교체하므로 쓰기 실패 시 이전 파일을 유지한다. 시작 시 손상된 자동 저장을 발견하면 다음 자동 저장 전에 `.invalid` 사본을 보존한다. 저장 위치에 쓰기 권한이 없으면 오류를 표시한다. 강제 프로세스 종료·전원 차단에는 종료 저장을 보장할 수 없다.
- 저장 테스트: `godot --headless --path . res://tests/save_system.tscn`. 실제 저장과 별개인 `.godot` 아래에서 자동 슬롯과 수동 슬롯 10개, 이전 파일 이동·재시도, 저장·복원, 큰 환생 정수, 손상 파일·쓰기 실패, UI 동작, 백그라운드 자동 저장·시작 복원을 검사한다. 일반 종료와 종료 요청을 각각 검사하려면 `-- --close-request` 옵션으로 한 번 더 실행한다. 다른 테스트 장면은 저장 시스템을 초기화하지 않아 실제 세이브에 영향을 주지 않는다.

## 구매 버튼 배치

- `scenes/button_layout.tscn`을 Godot의 2D 편집기에서 열면 모든 구매 버튼과 설명의 배치를 확인할 수 있다. `WorldReference`는 현재 `world_layout`을 흐리게 표시하는 잠긴 참고용 인스턴스다.
- `Buttons/그룹/버튼 ID/PurchaseButton`을 움직이면 구매 버튼 위치가 바뀌고, 같은 ID의 `InfoLabel`을 움직이면 설명 위치가 바뀐다. ID 노드를 움직이면 둘을 함께 옮길 수 있다. 크기와 스케일도 이 씬에서 지정한다.
- 저장 후 게임을 다시 실행하면 `button_layout`의 버튼·설명 노드를 복제해 좌표·크기·텍스처·글꼴·테두리 설정을 그대로 사용한다. 게임은 참고용 씬을 숨기고 복제한 UI에 해금·구매 처리와 최소 화면 크기 보정을 연결한다. 설명 내용은 최신 `ButtonData`에서 갱신한다.
- 버튼과 설명의 배치는 이 씬에서만 관리한다. 월드 오브젝트 위치를 바꾼 경우 참고용 배치를 보고 버튼 위치도 조정한다.
- `res://data/buttons`의 버튼 리소스를 열고 `Purchase Description > Description`에 여러 줄 설명을 입력한다. 비워 두면 효과 설명을 자동으로 사용한다. `button_layout`의 각 ID 노드는 해당 리소스에 연결되어 설명·이름·가격·효과를 수정하면 편집기 미리보기가 즉시 갱신된다. 설명은 `InfoLabel.text`에 별도로 저장하지 않는다.
- 새 월드 구매 버튼을 추가할 때에는 `Buttons` 아래에 버튼 ID와 같은 이름의 `Node2D`를 만들고 `scripts/ButtonLayoutEntry.gd`를 연결한다. `Button Data`에 해당 버튼 리소스를 지정하고, 수입원 관련 효과라면 `Income Source`도 지정한다. 자식으로 `PurchaseButton`(`TextureButton`)과 `InfoLabel`(`Label`)을 넣는다. ID가 누락되거나 중복되면 오류를 표시하고 해당 버튼의 구매를 막는다.

## 오류 처리

- `ErrorManager`는 가장 먼저 생성되는 Autoload이며, 오류 메시지는 HUD보다 위인 CanvasLayer 100에 표시한다. `PrestigeManager`는 짬 조건을 검사하는 `ButtonManager`보다 먼저 생성된다.
- 중복 ID는 첫 번째 항목을 임의로 선택하지 않고 조회·구매를 거절한다. 잘못된 수입원은 실행 상태에서 제외하며, 월드 구성이 잘못된 버튼은 구매할 수 없다. 필수 UI 노드가 없으면 해당 화면을 비활성화한다.
- 자금·배율의 유효하지 않은 수치와 큰 수의 지원 지수 범위 초과를 알린다. 실패한 결제와 환생은 기존 상태를 유지한다. 매우 큰 값은 약 15자리 유효숫자로 계산하며, 잔액에 즉시 표현되지 않는 작은 입출금은 별도 잔여값으로 누적한다. 수입원별 소수 원과 계산 잔여값도 보관하고 저장한다. 환생 짬도 정수 범위를 넘으면 근사 큰 수로 계산한다.
- 같은 `code`와 `context`는 세션 중 한 번만 표시하고 발생 횟수를 누적한다. 서로 다른 오류는 확인 버튼으로 차례대로 볼 수 있으며, 이력은 최대 100개까지 보관한다. 한도를 넘으면 `ERROR_LIMIT` 알림으로 추가 오류가 있음을 알린다.
- 자금 부족, 아직 해금되지 않은 버튼, 중복 클릭, 보상 없는 환생은 정상적인 거절이므로 오류 창을 띄우지 않는다.

다른 게임 로직에서도 같은 경로로 오류를 보고한다.

```gdscript
ErrorManager.report_error("ERROR_CODE", "사용자에게 보여 줄 오류 설명", "발생 위치 또는 ID")
var errors := ErrorManager.get_errors() # 외부에서 수정할 수 없는 이력 사본
ErrorManager.clear_errors() # 이력·대기 메시지·중복 표시 상태 초기화
```

실행 중 보호 경로의 오류를 처리한다. 스크립트 문법 오류나 Autoload 생성 전의 `preload` 실패처럼 게임 시작 자체를 막는 오류는 Godot 디버거·로그에서 확인해야 한다.


## 렌더링
### 장면 깊이
- 하늘(-100) < 구름(-90) < 실내 뒷배경/벽지(-20) < 전경/창문(-10) < 가구/인물/조리대(0) < 앞쪽 테두리/기둥/주춧돌/천장(10) < 땅(20) < 구매 버튼(30) < 설명/생산 타이머/말풍선(40)
- 공통 레이어 이름과 값은 `scripts/RenderOrder.gd`에서 관리한다. 구매 종류(`ButtonData.Type`)와 효과는 렌더링 순서에 관여하지 않는다.
- 월드의 깊이는 `world_layout.tscn`에서 지정한다. 노드에 `SceneRenderLayer.gd`를 연결하고 인스펙터의 `Rendering > Render Layer`를 선택하면 된다. 자식은 부모 레이어를 상속하며, 벽지처럼 다른 깊이인 자식에는 별도로 레이어를 지정한다.
- 구매 후 생성되는 스프라이트는 원본의 부모까지 포함한 실제 z-index를 보존한다. 같은 깊이에서는 월드 레이아웃의 노드 순서를 따른다.
- 화면 설명/툴팁은 CanvasLayer 1, HUD는 CanvasLayer 2에 표시되어 HUD가 월드와 모든 월드 설명보다 앞에 그려진다.
